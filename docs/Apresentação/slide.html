Problema

Um método faz tudo

Escolhe a oferta, calcula, monta o texto e altera o recibo. Tudo no mesmo lugar.

Solução

Cada regra virou uma classe pequena. O carrinho só guarda itens.

Problema

Muitos "se / senão"

Para criar uma promoção nova era preciso mexer no meio do fluxo e arriscar quebrar as outras.

Solução

Padrão Strategy: uma classe por promoção, escolhida pela fábrica.

Problema

Conta repetida

Pacotes de 2 e de 5 repetiam a mesma lógica de "preço cheio menos preço da oferta".

Solução

Uma única regra de pacote, com o tamanho como parâmetro.

Defeito real

Divisão errada no "2 por X"

Com 3 itens a conta dava R$ 32,50 em vez de R$ 25,00, e o desconto ficava positivo.

Solução

Registramos o defeito na linha de base e usamos divisão inteira, protegida por testes.

Problema

Estado interno exposto

Dava para limpar a lista de fora e a compra ficava inconsistente. Também aceitava quantidade negativa.

Solução

Listas viram tuplas imutáveis e as regras são validadas na criação do objeto.

Problema

Caixa e carrinho amarrados

Uma oferta por produto único: impossível criar combos.

Solução

Fluxo em uma direção só, várias ofertas ativas e reversão por commit se algo der errado.

Padrões de projeto aplicados Cada padrão resolve um problema real do código

Strategy

Uma classe para cada promoção

Problema: o "se / senão" gigante.
Exemplo: o combo de 10% entrou sem mexer em nenhuma oferta antiga.

Factory Method

Uma fábrica escolhe a estratégia

Problema: decidir qual classe criar.
Exemplo: passamos o tipo "combo" e os produtos e a fábrica entrega a estratégia pronta.

Repository / Gateway

O banco fica do lado de fora

O caso de uso conversa com contratos. Trocar o banco não muda a regra de negócio.

DTO

Dados planos para sair

O recibo é formatado a partir de dados simples, sem depender das entidades internas.

Decisões de arquitetura O que decidimos juntos e por quê

🧱 Clean Architecture + SOLID

O núcleo não conhece banco nem impressão. As dependências sempre apontam para o domínio.

✂️ KISS

Sem camadas e validadores extras. Entidades imutáveis e só o que realmente precisa existir.

🗄️ SQLite + SQLAlchemy

Duas tabelas simples: produtos e ofertas. Os produtos de uma oferta ficam em uma lista, sem tabela extra.

🔌 Interfaces pequenas (ISP)

Quem só consulta preço recebe um contrato de leitura. Quem cadastra recebe outro.

🧪 Memória só nos testes

Os repositórios em memória viraram apoio de teste. O código final usa apenas o banco.

🛡️ Validar na porta de entrada

O produto valida nome e unidade ao ser criado e o catálogo recusa preço negativo antes de gravar.

Convivência

Ofertas antigas vêm primeiro e avisam quantas unidades usaram. O combo só enxerga o que sobrou, então nunca há desconto duplicado.

Por que foi fácil

Criamos uma classe nova e registramos na fábrica. Nenhuma promoção antiga foi alterada.

combo_discount_strategy
def calculate_discount(self, cart, catalog):    qty = cart.product_quantities()    combos = min(int(qty.get(p, 0)) for p in self._products)    if combos < 1:        return None    base = sum(catalog.unit_price(p) for p in self._products)    return Discount(self._products, "Combo 10% off",                    combos * base * 0.10)

Banco de dados na prática SQLite + SQLAlchemy, de forma simples

Duas tabelas

offers: tipo da oferta, lista de produtos e valor.
